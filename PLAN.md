## Conclusion

As clarified by the product owner, CDIPL is a deterministic code generator. A developer writes intent in a file. A compiler assembles the program from a library of code blocks that have been verified in advance, in the way Lego bricks are assembled, and writes it out as folders of code in the chosen target language. No LLM writes code at any point. Generated code can be converted back to intent and traced to it. A fast classifier may help choose blocks from the library.

- **Coherent?** Yes, with four conditions.
  - **Reversibility** holds only for code the tool generated that is still in a form the tool would generate. The owner has accepted this: hand edits are allowed only if they convert back to intent.
  - **Several languages** requires the same intent to mean the same thing in every target. That is not automatic, even for sorting and comparing (see [Probe](#probe-the-same-operation-in-two-languages)).
  - **Blocks verified one at a time are not thereby verified in combination.** Blocks need declared input and output types, and the compiler must check every join.
  - **The classifier may suggest a block but must not choose one silently.** Otherwise a wrong guess becomes a wrong program, produced with no warning.
- **Worth pursuing?** Yes, as a staged experiment with a review after each stage. I expect the mechanics to work, because they are established compiler engineering. The real uncertainty is usefulness. With no way to embed hand-written code in the first version, a program can be generated only if every part of it exists in the library. Nobody has measured how much real code is like that.
- **Smallest proof of concept:**
  1. **Coverage audit**, with no code: measure, on real open-source programs, how much is made of reusable blocks and how much is one-off logic.
  2. **Pipeline slice**: six blocks from the proposal's own examples, compiled to Python and JavaScript, tested for identical behaviour, for every valid combination, for conversion back to intent, and for tracing.
  3. **Third target**: add Java, to measure what each additional language costs.

One caution about what Stage 2 can show. Small blocks in Python and JavaScript are the right place to prove the mechanics and the wrong place to prove value: the hand-written equivalent of the first example is one line. The value is in large blocks such as framework code, which the owner's roadmap reaches later, and that is also where keeping targets equivalent is hardest.

## Critique

### What holds up

- **A compiler, not a predictor.** The same input gives the same output, and every generated line has a known cause.
- **Refusing instead of guessing** (§3.2, §4, §11). Ambiguity produces a diagnostic.
- **Verified blocks as the unit of reuse.** Quality is established once per block, not re-argued for each generated program.
- **The owner's decisions narrow the problem.** Ruling out existing code and embedded hand-written code removes the hardest machinery in the proposal (§6.2 to §6.5) and makes the round trip between intent and code achievable.

### The product as clarified

1. **Without embedded hand-written code, coverage is all or nothing.** A program can be generated only if every part of it is in the library. If a script is 90% standard blocks and 10% logic particular to that script, CDIPL cannot produce it. Usefulness therefore depends on how much real code consists entirely of reusable blocks, and on whether a generated module can sit beside hand-written code that calls it (D2). Neither is known. Stage 1 measures the first.

2. **A library function is already a verified, reusable block.** `sorted(...)` in Python is one. The product needs a clear answer to "why generate code when I could call a library?" The candidate answers are: one description produces several languages; the output is plain code with no added dependency; every line traces to an intent. For small blocks the answer is weak, since the hand-written version of the proposal's first example is one expression: `sorted((u for u in users if u.age >= 18), key=lambda u: u.name)[:10]`. It becomes stronger as blocks get larger.

3. **Blocks verified one at a time are not verified in combination.** Joining blocks raises questions that no single block's tests answer: whether the output of one is a valid input to the next, name clashes, duplicate imports, and how errors pass between blocks. "Optimised" also does not carry over: a full sort followed by "limit 10" is two good blocks and a wasteful pair. Blocks therefore need declared input and output types, the compiler must check every join, and combinations must be tested as combinations.

4. **The same intent must mean the same thing in every language.** The probe wrote "sort by name" and "where age >= 18" the obvious way in Python and JavaScript. The two programs disagreed on all four checks. A specification of what each block means, independent of any target, has to exist before the second target is written.

5. **The roadmap mixes two kinds of growth, and each multiplies the work.** Java and C are new *targets* for the same intents. HTML with CSS, FastAPI, Django and React are new *kinds of intent*, each needing its own vocabulary and blocks. Every block has to be hand-built, tested and kept equivalent for every target that supports it. Framework blocks also have to follow each framework's releases. Stage 3 measures the cost of one added target.

6. **Value and difficulty rise together.** Large blocks such as "an authenticated endpoint" save real work, so the framework tiers are where the product is most valuable. They are also where "one intent, several targets" is hardest, because FastAPI and Django are different designs and not the same thing in two languages. The plan should not assume that results from Python and JavaScript carry over.

7. **The classifier needs a bounded role.** If intent is written in a fixed grammar, the grammar already determines the block and no classifier is involved. A classifier is useful when a developer describes what they want in their own words and needs to find the right block among many, which is a search problem. Used that way, it proposes candidates, the developer picks one, and the block's exact name goes into the intent file. A wrong suggestion then costs a moment. If the classifier instead chose silently, a wrong choice would produce a wrong program with no warning, and the same intent file could compile differently after the classifier is retrained. With six blocks, as in the proof of concept, there is nothing to search, so the classifier is deferred until the library is large.

8. **Generated sample applications cannot serve as the yardstick.** The owner suggested using AI-generated applications in place of real requests. Generated samples reflect what the generator considers typical. They are regular and tutorial-like, so they would overstate how much real code is made of standard blocks. They are useful for other purposes: as reference programs to test generated code against, and as first drafts of blocks, subject to decision D3. For measuring coverage, real code written by people is needed, and open-source code is available without the team's own data.

9. **Reversibility is now well defined, and still has to be demonstrated.** The rule is: converting a file back either returns an intent that regenerates that file exactly, or refuses. This is testable. *Assumption, from general knowledge: earlier model-driven tools that promised round trips between models and code struggled once developers edited the generated code.* The owner's rule avoids that by refusing such edits, at the price of developers being unable to adjust generated code freely.

### The proposal document

10. **No shared representation is shown.** The two examples in §5 have no fields in common. The representation is called typed, but the examples carry no types and do not say where `users` is bound. Block interfaces with declared types, as required in point 3, would supply what is missing.

11. **The proof of concept in §12 is superseded.** It tests the editing of an existing React project, which the owner has ruled out for the first version.

### Probe: the same operation in two languages

Five records, read from one JSON file. Each check is the obvious one-line implementation in each language, the kind a first version of a block would contain.

| Check | Python | JavaScript (Node) |
|---|---|---|
| Sort by name, where names include `～` (U+FF5E) and `😀` (U+1F600) | `～` before `😀` | `😀` before `～` |
| `age > 9007199254740992` for ages `…993` and `…992` | selects the first record | selects nothing |
| Output of ages written as `18` and `18.0` | `18`, `18.0` | `18`, `18` |
| `age >= 18` when one record has no `age` | raises an error | silently drops the record |

Reading: two straightforward translations of one intent are not the same program. Each difference has a known remedy, but each remedy is a decision the block's specification has to make and every target then has to implement. This is five records and two languages; it shows the problem exists, not how large it is.

## Recommended direction

1. **Treat the block library as the product.** Each block has a name, typed inputs and outputs, a written meaning, code for each supported target, a way to recognise that code when converting back, and tests.
2. **Write each block's meaning down before its second target.**
3. **Check every join at compile time,** using the declared types, and test combinations, not only single blocks.
4. **State reversibility as two testable rules.** Converting generated code back gives the original intent. Converting any file back either gives an intent that regenerates that file exactly, or refuses.
5. **Every target declares which blocks it supports.** The compiler refuses an unsupported block for that target; it never approximates.
6. **Keep the classifier out of the compiler.** When the library is large enough to need it, add it to the editor as a search aid whose result the developer confirms.
7. **Measure coverage on real code before building,** and review after each stage, as the owner asked.

## Proof of concept

### The hypothesis being tested

For one family of intents, a compiler can assemble verified blocks into programs in at least two languages that behave identically on the same input, in every valid combination; that convert back to exactly the intent they came from; and that trace line by line to it. Separately: a useful share of real code consists entirely of blocks that could be in such a library.

### Stage 1: coverage audit

No code. It tests critique point 1.

1. Choose at least 20 small real programs, half Python and half JavaScript, from open-source repositories. Fix the selection rule before reading any of them. Prefer scripts and small utilities, since those are the first tier of the roadmap.
2. Split each program into units: its functions, or the whole script if it has none.
3. Two people classify each unit independently, then record disagreements:
   - **Closed:** it could be stated entirely as a chain of named operations with parameters.
   - **Open:** it contains logic particular to that program.
   - For closed units, name the kind of operation (for example data pipeline, file reading and writing, argument parsing, HTTP request, text formatting).
4. Report the share of units that are closed; the share of whole programs in which every unit is closed; and how many distinct blocks would cover 50% and 80% of the closed units.

Known weakness: twenty programs is a small sample, and the choice of repositories can flatter or condemn the idea. Keep the raw records so the classification can be challenged.

### Stage 2: pipeline slice

**Blocks.** The six operations in the proposal's examples in §2 and §3.1.

| Block | Takes | Gives |
|---|---|---|
| Read a declared source | nothing | rows |
| Filter | rows | rows |
| Sort | rows | rows |
| Limit | rows | rows |
| Group by a field | rows | groups |
| Count each group | groups | rows of key and count |

**Language.**

```text
source users from "users.json":
    name: text
    age: integer
    school: text

get users where age >= 18
sort by name ascending
limit 10
```

- Fields have declared types: `integer` and `text`.
- Filters compare a field with a literal using `=`, `!=`, `<`, `<=`, `>`, `>=`, joined by `and`.
- One spelling per block. No synonyms and no classifier.
- No embedded target-language code.

**Specification.** One page that fixes, independently of any target: the ordering of text, the range of integers, what happens when a field is missing or has the wrong type, the order of groups, and the order of rows that tie in a sort. The probe shows why each needs an answer.

**Targets.** Python and JavaScript. Input is a JSON file of records; output is JSON. Generated programs contain plain code and depend on nothing supplied by CDIPL (D5).

**Commands.**

- `build`: reads an intent file and writes a folder containing the generated program and a trace file that maps each generated line to an intent line.
- `lift`: reads a generated program and returns the intent, or refuses.

**Tests.**

| Test | What is checked |
|---|---|
| Equivalence | A fixed set of at least 200 pairs of intent and dataset, including the edge cases from the probe, empty input, ties, and a limit larger than the data. Every target produces byte-identical output, or every target reports the same category of error. |
| Combination | Every chain of up to four blocks after the source is enumerated. Each chain whose types fit must build in every target and pass equivalence. Each chain whose types do not fit, such as counting groups that were never formed, must be rejected with a message naming the mismatch. |
| Round trip | For every test intent, `lift` of the built program equals the intent in normal form, with comments stripped from the program first, so that the intent is recovered from the code and not from an embedded copy. For every generated file, `build` of its `lift` reproduces the file exactly. |
| Edited code | At least 30 hand edits to generated files: changed literals, changes that stay within the vocabulary, and inserted foreign statements. `lift` either returns an intent that regenerates the edited file exactly, or refuses. |
| Trace | Every non-blank generated line maps to one intent line or is marked as fixed support code. Checked mechanically. |
| Quality | Generated code passes, with no findings, a formatter and linter configuration agreed for each target before the stage starts (D6). |
| Diagnostics | At least 20 invalid intent files (unknown field, type mismatch, unknown word, missing source). Each is rejected with a message naming the line. None compiles. |
| Determinism | Ten builds from a clean checkout produce byte-identical folders. |

Also record, for ten test intents, the generated program beside a hand-written equivalent, with line counts. This is not a pass or fail test. It is material for the discussion of value in critique point 2.

### Stage 3: third target

Add Java, from the owner's second tier. It is statically typed, so it tests whether the intent language's declared types carry enough information, and it is unlike the first two targets. C is the alternative.

*Assumption, not checked: Java's standard library does not read JSON, so generated Java would need either a third-party library or a simpler input format shared by all targets. This has to be settled before Stage 3 and may change the input format chosen in Stage 2.*

Record the effort relative to the second target, which parts of the specification needed special handling, and any dependency the generated code requires. The same tests apply. If Java cannot meet the specification for a block, the target must declare it and the compiler must refuse that block for Java.

### Not included

The classifier, editing of existing code, embedded target-language code, markup and framework blocks, IDE integration, performance measurement, and any family beyond the first.

### Suggested time budget

*My estimates, not validated:* two to four days for Stage 1, two to three weeks for Stage 2, and about one week for Stage 3, for one engineer. Agree a hard stop for each stage before starting it (D8).

## Evidence that would count as success

Fix these before any result is seen. The numbers are proposals for the team to ratify. The Stage 1 numbers are judgment calls with no empirical basis.

**Stage 1.**

| Share of units that are closed | Reading |
|---|---|
| 30% or more | Enough real code is made of blocks for generated modules to be useful. Continue. |
| Between 10% and 30% | Team decision. Usefulness will depend on generated modules working beside hand-written code (D2). |
| Below 10% | A block library without embedded hand-written code covers too little. Stop, or revisit that decision. |

Report the share of whole programs that are entirely closed alongside this. If it is near zero, the first version cannot generate complete programs, whatever the unit figure is.

**Stages 2 and 3. All must hold.**

| ID | Criterion |
|---|---|
| G1 | Equivalence: no pair on which targets differ. |
| G2 | Combination: every chain whose types fit builds and passes; every chain whose types do not fit is rejected. |
| G3 | Round trip: holds for every test intent and every generated file, in every target. |
| G4 | Edited code: `lift` never returns an intent that fails to regenerate the file it was given. One such case fails the stage. |
| G5 | Trace: complete, with no unmapped lines. |
| G6 | Quality: no formatter or linter findings in any generated file. |
| G7 | Diagnostics: every invalid file rejected with its line; none compiled. |
| G8 | Determinism: byte-identical output across ten builds. |
| G9 | The specification was written before the second target, and every difference found between targets was resolved by changing the specification or a target, not a test. |
| G10 | Stage 3 only: the effort for the third target is recorded, and any unsupported block is refused by the compiler, not mistranslated. |

**What would disprove the idea.** Stage 1 below its floor disproves usefulness for the first version as scoped. Failure of G1 or G2 that can be fixed only by restricting the blocks until they are no longer useful disproves the multi-target or the Lego claim for this family. Failure of G4 disproves reversibility as stated.

**What success would not show.** That developers prefer this to writing the code or to an LLM assistant; that markup or framework blocks work; that many kinds of intent in many languages can be maintained at acceptable cost; that it works inside an IDE.

**What happens next.**

| Outcome | Next step |
|---|---|
| All stages pass | Start the roadmap below, one step at a time, choosing the next kind of intent from the Stage 1 ranking |
| Stage 1 passes; G1 or G2 fails | Reduce to one target language and re-examine the claim that failed |
| Stage 1 lands in the middle band | Decide D2 before Stage 2 |
| Stage 1 fails | Stop before writing the compiler, or revisit the decision on embedded code |

## Roadmap after the proof of concept

This follows the owner's order. Each step adds either a target for existing blocks or a new kind of intent, and each should pass the same tests before the next begins. It is a direction, not a schedule; nothing beyond Stage 3 is planned in detail.

| Tier | Owner's item | What it adds | What is new and untested |
|---|---|---|---|
| 1 | Python, JavaScript | First two targets | Covered by Stages 1 and 2 |
| 2 | Java, C | More targets for the same blocks | Static types; memory management in C; Stage 3 covers Java |
| 2 | HTML with CSS | A new kind of intent: pages and layout | A new vocabulary. "Identical behaviour" needs a new definition, because the output is rendered, not computed. |
| 3 | FastAPI, Django | New kinds of intent: endpoints and data models | Large blocks; dependence on framework versions; whether one intent can target two frameworks at all |
| 4 | React with CSS | A new kind of intent: stateful components | State and events; equivalence across UI frameworks |

Introduce the classifier, as a search aid in the editor, at whichever tier the library becomes too large to browse.

## Out of scope: editing existing code

The owner has decided that the first version does not work on code it did not generate. The proposal's transformation mode (§6.2 to §6.5, §8, §12) is therefore out of scope.

For the record, revision 1 of this plan examined it and ran a browser probe on nine simple cases of "make this element 10% wider". The browser reported the exact file, line and column of every matching width declaration. The proposal's rule of multiplying the declared width failed in five of the nine cases: three had nothing to edit, one produced no visible change, and one gave 7.9% in place of 10%. The full results, and a design for a proof of concept, are in revision 1 of this file at commit `d23ae96`.

## Major risks

| Risk | Why it matters | Mitigation |
|---|---|---|
| Too little real code is made entirely of blocks | Without embedded code, partial coverage of a program is no coverage | Stage 1 runs first and needs no code; decision D2 |
| Cost grows with kinds of intent multiplied by targets | Every block is hand-built per target and must stay equivalent; framework blocks must follow framework releases | Stage 3 measures one added target; one roadmap step at a time |
| Targets drift apart in meaning | The probe found four differences in two operations | Written specification; equivalence tests on every change (G1, G9) |
| Blocks interact badly when combined | Verification of single blocks does not cover joins | Typed interfaces; the combination test (G2) |
| Developers cannot adjust generated code | Edits that do not convert back are refused, by the owner's rule | Accepted for the first version; watch for it in early use |
| Small blocks offer little over a library call | Stage 2 may pass and still look unimpressive | State in advance that Stage 2 proves mechanics; value is judged at the framework tiers |
| A classifier that chooses silently | Wrong block, wrong program, no warning | Decision D1: suggest and confirm only |
| Existing tools already do this well | Not evaluated in this review | A prior-art survey before Stage 2 is recommended |
| Scope returns to "everything at once" | The proposal's breadth is its main delivery risk (§10.9) | The roadmap's one-step rule and a review after each stage |

## Appendix: probe inputs and method

Input (`data.json`):

```json
[{"name":"～","age":9007199254740993},{"name":"😀","age":9007199254740992},{"name":"b","age":18},{"name":"B","age":18.0},{"name":"a"}]
```

| Check | Python | JavaScript |
|---|---|---|
| Sort | `sorted(d, key=lambda u: u['name'])` | `sort` with a comparator using `<` and `>` on `name` |
| Large integers | first two records, `u['age'] > 9007199254740992` | first two records, `u.age > 9007199254740992` |
| Number output | `json.dumps` of the ages of records 3 and 4 | `JSON.stringify` of the same |
| Missing field | `[u for u in d if u['age'] >= 18]` | `d.filter(u => u.age >= 18)` |

Full sort results: Python gave `B, a, b, ～, 😀`; JavaScript gave `B, a, b, 😀, ～`.
